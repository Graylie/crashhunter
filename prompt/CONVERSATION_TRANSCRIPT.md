# CrashHunter 项目开发对话记录（简化整理版）

> 说明：本文按项目开发主题整理交流内容，合并重复问答并简化表述，保留主要设计思路、操作方法和验证内容。

**用户：**

我想做一个 Android 软件动态测试平台，主要功能是输入一个 APK 所在的目录，然后自动运行里面的软件，通过模拟用户操作来测试，最后检测有没有崩溃。准备用 Python 写，这个整体应该怎么实现？

**ChatGPT：**

这个项目可以理解为一个自动化测试工具，核心流程其实比较清晰：

首先通过 Python 扫描你指定的目录，找到 APK 文件；然后通过 ADB 将 APK 安装到模拟器或手机上；安装完成后启动应用，再利用 Android Monkey 模拟用户操作，比如点击、滑动、返回和页面切换。

测试过程中，Python 还需要持续读取 Android 的 Logcat 日志，判断应用是否出现异常。

我建议先不要急着把所有功能写在一起，可以拆成几个模块：

- APK 扫描和安装；
- Android 设备管理；
- Monkey 随机事件测试；
- 崩溃日志分析；
- 测试证据保存；
- 自动生成测试报告。

这样后续增加功能时会容易维护一些。

**用户：**

那是不是必须用 Appium？我看很多 Android 自动化测试项目都用这个。

**ChatGPT：**

不一定。你的项目目前主要是通过随机事件测试应用，并不需要特别复杂的自动化界面操作。

可以直接使用 Android SDK 自带的 ADB 和 Monkey，不需要额外引入 Appium，也不需要安装第三方 Python 库。

Python 负责组织测试流程，通过 `subprocess` 执行系统命令即可。

例如，检查设备：

```powershell
adb devices -l
```

安装 APK：

```powershell
adb install -r app.apk
```

启动应用之后，再调用 Monkey：

```powershell
adb shell monkey -p com.example.app 300
```

这里的包名需要替换成实际 APK 的包名。

**用户：**

明白了，那 APK 的包名怎么获取？我不想让用户自己输入包名，最好能自动识别。

**ChatGPT：**

这个功能可以放在 APK 扫描模块中。

APK 本质上是一个包含应用资源和配置文件的压缩包，其中有 AndroidManifest.xml，可以从中解析包名和版本信息。

建议扫描 APK 时同时计算 SHA-256，这样测试报告中可以记录具体测试的是哪个版本的安装包。

另外，目录中可能有多个 APK，所以最好设计成逐个扫描、逐个安装和测试，而不是只处理第一个文件。

**用户：**

还有一个问题，如果电脑同时连接了模拟器和手机，ADB 会不会不知道应该操作哪一个？

**ChatGPT：**

会，所以这里最好增加设备选择参数。

可以通过 `adb devices -l` 获取所有设备的序列号，然后通过 `-s` 指定目标设备。

例如：

```powershell
adb -s emulator-5554 install -r app.apk
```

你可以在命令行中增加一个 `--device` 参数。如果只连接一台设备，可以自动选择；如果有多台设备，则要求用户明确指定。

另外，设备状态不是 `device` 时，不应该继续执行测试，否则后面的错误可能会很难定位。

**用户：**

那测试部分我想用 Monkey，每次测试300个事件，连续测试三轮，每轮的随机操作不一样，但是最好还能复现。

**ChatGPT：**

这个可以通过随机种子实现。

建议增加几个参数：

- `--events`：每轮事件数量，默认300。
- `--rounds`：测试轮数，默认3。
- `--seed`：初始随机种子。
- `--throttle`：事件之间的时间间隔。
- `--timeout`：单轮测试的最长执行时间。

比如你设置：

```powershell
python -m code.src.crash_hunter.android --target targets/my-app --sdk E:\AndroidStudio\Sdk --device emulator-5554 --events 300 --rounds 3 --seed 2026
```

三轮可以分别使用2026、2027、2028作为随机种子。

不过需要注意，随机种子只能帮助重新生成相同的事件流，不能保证不同设备、不同应用数据状态下完全复现相同的运行结果。

**用户：**

我还希望每轮开始之前把应用重新启动一下，不然上一轮的状态可能影响下一轮。

**ChatGPT：**

可以。每轮测试开始前先停止目标应用，再重新启动。

不过停止应用和清除应用数据是两回事。你目前的需求只需要停止并重新启动，不一定要清除数据。

建议默认不清除数据，另外单独提供一个 `--reset-app-data` 参数，需要干净状态测试时再使用。

这样既能保留应用的正常运行状态，也能满足特殊复测需求。

**用户：**

接下来就是崩溃检测了。Android 崩溃是不是只要搜索 Logcat 里面的 FATAL EXCEPTION 就行？

**ChatGPT：**

这是一个比较常见的做法，但只搜索 `FATAL EXCEPTION` 不够。

Android 应用的异常至少需要考虑三种情况：

1. Java 崩溃：例如 `FATAL EXCEPTION` 和 `AndroidRuntime` 中的异常堆栈。
2. Native 崩溃：例如 `Fatal signal`、Native Crash 和相关 tombstone 信息。
3. ANR：应用无响应，需要结合 Monkey 输出和系统日志判断。

还有一个很重要的问题：不能把整个设备的所有崩溃都算成目标应用的问题。

例如，后台可能还有其他应用发生异常，所以需要结合目标包名、进程 PID 和子进程关系进行筛选。

**用户：**

那如果一个崩溃在日志里面出现很多次呢？我不想报告里面重复出现相同的问题。

**ChatGPT：**

可以增加问题去重机制。

例如，把目标包名、异常类型、异常位置和关键堆栈组合起来，生成一个问题指纹。

如果不同轮次出现了相同指纹，就认为是同一个问题，将多次发生记录关联起来，而不是重复创建 BUG 编号。

报告里面还可以保留每次发生的时间、对应轮次和日志证据。

**用户：**

我希望最后生成的报告不只是一个简单的文本，最好有 HTML 页面，可以直接查看问题详情。

**ChatGPT：**

那建议同时生成三种格式：

- Markdown：方便阅读和编辑。
- HTML：方便直接通过浏览器查看。
- JSON：方便其他程序进一步读取测试结果。

每次测试可以创建一个带时间戳的目录，例如：

```text
reports/
  android-时间戳/
    report.html
    report.md
    summary.json
    app-01-round-01/
    app-01-round-02/
    bugs/
      BUG-001/
```

其中每一轮单独保存 Monkey 输出、Logcat、测试参数、启动记录以及开始和结束截图。

如果发现崩溃，再创建对应的 BUG 目录，保存异常堆栈、证据和复测命令。

这样后面排查问题就不需要重新翻整个测试日志了。

**用户：**

随机测试有个问题，就是有些 Bug 必须按照固定的操作顺序才能触发。如果完全随机点击，可能一直复现不了。能不能再加一个指定步骤的测试模式？

**ChatGPT：**

可以，这个功能比较适合单独设计成 JSON 测试用例。

比如用户可以提前写好一系列操作，程序按照顺序执行。

不过我建议不要完全依赖屏幕坐标，因为不同模拟器的分辨率可能不同，界面位置也可能发生变化。

你可以通过 ADB 获取当前界面的 UI XML，然后优先根据控件的 `resource-id` 或文本定位。

每执行一步操作，就重新获取一次界面信息，再寻找下一步需要操作的控件。

如果某一步找不到对应控件，就停止测试并保存当前 UI XML 和截图，不要直接随机点击其他位置，否则测试流程就不准确了。

**用户：**

这个和 Monkey 模式是不是可以共存？我不想因为增加这个功能，把原来的随机测试改掉。

**ChatGPT：**

可以共存，而且最好保持两个模式相互独立。

随机测试继续使用 Monkey，适合探索未知操作路径。

明确步骤测试使用 JSON 用例，适合复现已知问题。

可以通过 `--scenario` 参数决定是否启用步骤测试。如果没有指定，就运行原来的 Monkey 随机测试。

这样原有功能不需要改变。

**用户：**

我想找一个真实的 Android 应用测试一下，不想只用自己写的 Demo。最好还能找到一个确实存在的崩溃问题。

可以选择有公开历史 Issue 的开源应用。

这里需要区分一下，这是复现已有公开缺陷，并不是你新发现的漏洞。

**用户：**

这个测试过程能不能也录下来？我想在项目展示的时候直接播放。

你还可以为明确步骤测试保存每一步的操作记录、UI XML 和截图，这样视频之外还有更详细的过程证据。

需要注意，视频和截图是辅助证据，真正判断崩溃仍然要依靠日志和异常堆栈。

**用户：**

除了 LibreNews，我还想找一个没有已知缺陷的应用，做一下随机测试，证明平台不是只能复现固定问题。

最后代码结构怎么组织比较合适？我现在功能越来越多，有点担心代码都堆在一起。

**ChatGPT：**

根据目前的功能，建议把代码组织成下面这样：

```text
CrashHunter/
├── code/
│   ├── src/
│   │   └── crash_hunter/
│   │       ├── android.py
│   │       ├── ui_scenario.py

│   │       ├── runner.py
│   │       ├── fuzz.py
│   │       └── reporter.py

│   ├── tests/
│   └── examples/
├── targets/
├── reports/
├── video/

```

其中：

- `android.py` 负责 Android 设备操作、APK 安装和崩溃检测。

- `reporter.py` 负责测试报告生成。
- `tests/` 保存自动化测试。
- `examples/` 保存真实应用测试案例。
- `video/` 保存实际运行录像。

这样后续维护和扩展都会比较方便。

那我建议把项目的重点放在两个方面：

一方面是通用性，通过 APK 目录扫描、Monkey 随机测试和多轮测试机制，支持不同 Android 应用的自动化动态测试。
